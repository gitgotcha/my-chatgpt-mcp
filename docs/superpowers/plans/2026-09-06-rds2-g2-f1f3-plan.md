## 2. G2-F1 [P1] 有界 staging 状态（修订）

### 2.1 根因（不变）

- `algorithm.js:214–330` `buildPage` 把 `topics{}`、`problems{}`、`latestByTopic{}` 三份全历史字典放进 `continuation`。
- `builds.js:304–311` 整份回写 `savedContinuation`。
- `migrations/0006_rds2_v2_tables.sql:126` 约束 `continuation_json … length(...) <= 65536`。
- 字节随「不同专题数 + 不同题目数」单调增长，第 5 页触发 CHECK → 落入 §3 的 defer 死循环。

关键观察（不变）：每页已把 topic/problem 累计值以键控行 upsert 进 staging generation（`builds.js:321–336`），reducer 只是读不回来。

### 2.2 接口：声明式读取计划 + 引擎执行 + 纯函数折叠（**修订**）

原稿给出异步 `readStaged` 却未 `await reducer.buildPage(...)`，不可直接实现。改为三段式，**`buildPage` 保持纯同步函数**：

```js
// ① reducer 声明本页需要读什么（纯函数，无 IO、无 await）
const plan = reducer.planPageReads({ events });
//   → { reads: [ { rowKind: "topic",   rowKeys: [...] },
//                { rowKind: "problem", rowKeys: [...] } ] }
//     rowKeys 由 reducer 去重、顺序稳定；不含 IO

// ② 引擎校验并执行（有界、可预算、可被拒绝）
const staged = await readStagedWithinBudget({
  io, scope, stagingGeneration, plan, maxCalls: 4
});
//   → { topic: Map, problem: Map }
//
//   scope 与 stagingGeneration 一律由引擎从权威构建行取得，**不由 reducer 传入**：
//   每条查询都必须同时绑定 userId、namespace、projectionName、generation 四段。
//   引擎在**外发任何一次查询之前**完成计划校验、同类合并、去重与总成本测算 ——
//   不允许「先发 4 次才发现计划需要第 5 次」。若去重分块后仍超过 maxCalls，
//   直接抛 `build_read_limit_exceeded`（D 类），一次查询都不发。

// ③ 纯折叠
const pageResult = reducer.buildPage({ scope, events, head, continuation, staged });
```

`readStagedWithinBudget` 的**引擎强制约束**（不是 reducer 自律）：

1. `rowKind` 必须在白名单 `{ topic, problem }` 内，否则确定性拒绝；
2. 单个 `rowKind` 的 key 数 ≤ 本页事件数（≤ `pageSize` ≤ 50）；
3. 分块：每块 ≤ 32 个 key，SQL 必须形如
   `… WHERE user_id = ? AND namespace = ? AND projection_name = ? AND generation = ?
      AND row_kind = ? AND row_key IN (?, ?, …)`，
   **四段 scope + generation 全绑定**，走既有唯一键点查，非扫描；
3b. **发前测算**：先按去重后的键数算出块数与总调用数，超出 `maxCalls` 就在**发第一次之前**拒绝；
3c. **同类合并与去重**：同一 `rowKind` 的 key 先去重再分块，重复键不产生额外查询；
4. **总调用次数 ≤ 4**，第 5 次直接抛 `build_read_limit_exceeded`（D 类），不静默退化为「少读几个键」；
5. 每次调用都经 `io.db` 包装计数，**失败的读取同样计数**（`budget.js` 先 consume 后发出）；
6. 引擎在业务阶段开始前检查预算预留（§5），预留不足时不得进入读取阶段。

由此 reducer **无法**通过反复调用读取接口消耗预算：它只声明一次计划，执行权与次数上限都在引擎。

### 2.3 调用次数上界与配额（裁定：接受 4 次，但引擎强制、总量满足 24）

- 本页不同 key 数受页长限制：`topic` ≤ 50、`problem` ≤ 50 → 每 kind 最多 2 块（块长 32）→ **合计 ≤ 4 次**。
- 这 4 次计入投影配额 24 之内，完整账目见 §5。**验收口径是「总调用 ≤ 24」而非「低于 40」**。
- 不强求合并为单次 `row_kind IN (…)` 查询（裁定接受 4 次）；若后续实测希望降为 2 次，作为优化项，不阻塞本轮。

### 2.4 页内重复键：必须读页内更新后的值（**修订新增**）

同一页内重复出现同一专题或题目时，必须更新**页内临时 Map**，后续事件读取的是更新后的值，不能每次都从预读值重新计算：

```js
const working = new Map(staged.topic);        // 页内可变副本
for (const event of events) {
  const current = working.get(topic) ?? null; // ← 读页内当前值，不是预读快照
  const next = updateTopic(current, { outcome: learning.outcome });
  working.set(topic, next);                   // 后续事件看到更新后的值
  rowChanges.push({ rowKind: "topic", rowKey: topic, value: next });
}
```

`problem` 同理。`latestByTopic` 不再单独保存：topic 行 value 已含 `lastObservedAt`/`lastEventId`/`lastOutcome`，用 `latestWins` 对页内当前值与本次候选比较即可重算，等价且省一份字典。

回归面：跨页回访已有键、页内重复键、页内重复键且后一次是更晚事件（胜者应更新）都必须累计正确。

### 2.5 字节上界：不预设数值，先消除字典再量测（**修订**）

原稿「上限 ≤ 4KiB」是拍脑袋，撤回。原因：`topic`、`username` 等是用户可控的**变长**字符串，字段数量固定不等于字节固定。

新口径：

1. **消除全历史字典**（`topics{}`/`problems{}`/`latestByTopic{}`），continuation 只保留定长标量 + 单个 head + 固定 4 个计数；
2. **不重复保存 summary 已有字段**：`counts`、`latest`、`headIdentity`、`lastReceivedEventId` 只存一份，不在 continuation 顶层与 `summary` 内各存一遍；
3. **量测得出上界 C 并写死为观测断言**（`continuationBytes ≤ C`），C 由实测记录，**C 只作断言，不作拒绝阈值**；
4. **事务前校验**各受限单元，**限额按对象分别适用**（原稿一律写 64KiB 会误拒绝合法归档，已修正）：

   | 对象 | 保留限额 | 超限处理 |
   |---|---:|---|
   | `continuation`、`summary`、单行 `value_json` | **64 KiB** | `build_state_too_large`（D 类，停车，不 defer） |
   | `packageJson`、`activationJson`（归档对象） | **256 KiB** | 沿用既有归档超限码，**不并入** `build_state_too_large` |
   | 行变更集合 | 既有限额 | 沿用 `changes_too_large` |

   错误码保持分列，不全部合并：`build_state_too_large` 只表示**构建状态**超限；
   既有行变更、归档超限码继续表达各自语义。

5. **不得新增更小限制**：不引入任何低于上表既有值的自定义拒绝阈值，避免原本能正常处理的合法输入被无依据拒绝。量测出的 C 仅用于暴露回归，不用于拒绝。

### 2.6 量测场景表述修正（**修订**）

原稿「同一 35 条事件构造 200/1000 个专题」表述错误（35 条事件造不出 1000 个专题）。修正为：

- 分别构造 **35 条、200 条、1000 条或更多**事件，各自带不同专题与不同题目；
- 每组断言：构建可完成、重放等于在线结果、`readStaged` 调用次数 ≤ 4、continuation 字节 ≤ C；
- **不得只复用一个专题和一道题**，否则无法暴露累计状态增长。

## 3. G2-F2 [P1] 错误分类与真实故障生命周期（修订）

### 3.1 前置动作：先用双绑定验证异常形状（**修订新增**）

裁定指出：数据库守卫用 `RAISE(ABORT, 'stale_task_write')` 等错误文本，真实 D1 **未必提供同名 `error.code`**。

实测确认：当前 `src/` 中**完全没有** `stale_task_write` / `cursor_regression` / `build_requires_building` 的任何识别点 —— 这些受控错误目前一律落进通用 catch 被 defer。

因此实施第一步不是写分类，而是**探测**。**已于 2026-09-06 完成探测，实测结果如下**（探针：
`.rds2-probe-f2-shape.mjs`，未提交，待断言进入正式测试后删除）。

#### 3.1.1 实测异常形状

| 绑定 | `error.code` | `error.message` | `error.cause` | 守卫标记所在 |
|---|---|---|---|---|
| SQLite 模拟器 | `"ERR_SQLITE_ERROR"` | **恰为守卫文本**，如 `cursor_regression` | 无 | `error.message` |
| Miniflare/workerd D1 | **`null`** | `D1_ERROR: cursor_regression: SQLITE_CONSTRAINT (extended: SQLITE_CONSTRAINT_TRIGGER)` | 有，`cause.message` = `cursor_regression: SQLITE_CONSTRAINT (…)`，`cause.code` 也是 `null` | `error.message` 与 `error.cause.message` |

对照组（普通 SQL 错误，非守卫）：SQLite `no such table: rds2_no_such_table`；
D1 `D1_ERROR: no such table: rds2_no_such_table: SQLITE_ERROR`；两者 `code` 均非守卫标记。

**结论（直接决定实现方式）**：

1. **两种绑定都不提供等于守卫名的 `error.code`** —— 审核的预判成立
   （SQLite 给 `ERR_SQLITE_ERROR`，D1 给 `null`）。
   分类**必须**基于消息/原因文本中的**守卫标记**，不能依赖 `error.code`。
2. **在条件隔离的前提下，守卫 → 标记是确定的 1:1 映射，两种绑定完全一致**（§3.1.2）。
   转换层因此**必须保留具体标记**，再结合操作上下文定类别，**不得把多个守卫合并成一类**。
3. 辅助判据（仅用于加速，不作唯一依据）：SQLite `errcode` `1811` = 触发器中止、
   `275` = CHECK、`1` = 一般 SQL 错误；D1 用 `extended: SQLITE_CONSTRAINT_TRIGGER` /
   `SQLITE_CONSTRAINT_CHECK` / `SQLITE_ERROR`。

> **已撤回的错误结论（第一版探针）**：初版用 `no-such-task` 触发 `stale_task_write`，
> 该构造**同时**违反任务守卫与投影关联守卫，得到的是 `stale_projection_revision`。
> 我当时据此断言「触发器执行顺序不确定、应把整个守卫标记集归为同一类」—— **这是错的**。
> 一个用例同时踩中多个失败条件，只说明存在多个失败条件，不能据此合并任何类别。
> 隔离条件后重测（§3.1.2），每个用例在两种绑定上都只产生**唯一且确定**的标记。

#### 3.1.2 隔离条件下的 1:1 标记映射（实测）

每个用例只违反**一个**条件、且使用独立的 `user_id`，schema 每绑定只 apply 一次。
两种绑定对每个用例都给出**同一个标记**，无歧义、无顺序依赖：

| 用例（只违反该条件） | 标记 | SQLite 载体 | D1 载体 |
|---|---|---|---|
| 租约 owner 不匹配（其余全有效） | `stale_task_write` | `message`，`errcode 1811` | `message` / `cause.message` |
| 租约 epoch 不匹配 | `stale_task_write` | 同上 | 同上 |
| 租约已过期 | `stale_task_write` | 同上 | 同上 |
| `expected_revision` 与 head 不符（租约全有效） | `stale_projection_revision` | 同上 | 同上 |
| 缺 `expected_revision`（projection 任务） | `guard_requires_expected_revision` | 同上 | 同上 |
| `last_event_seq` 倒退 | `cursor_regression` | 同上 | 同上 |
| 未置 `building=1` 即插入 build | `build_requires_building_flag` | 同上 | 同上 |
| 置 `building=1` 后插入 build | **成功**（证明前一行确实只违反一个条件） | — | — |
| continuation 合法大小更新 | **成功**（证明目标行存在） | — | — |
| continuation 超 64 KiB | `CHECK constraint failed: continuation_json IS NULL OR (json_valid(…) AND length(…) <= 65536)` | `errcode 275` | 同文本 + `extended: SQLITE_CONSTRAINT_CHECK` |
| 普通 SQL 错误（对照） | 无守卫标记，`no such table: …` | `errcode 1` | 同文本 + `SQLITE_ERROR` |

**continuation 64 KiB CHECK 已补齐有效样本**（第一版因目标行不存在而无效）：
先置 `building=1` → 插入 build 成功 → 合法大小更新成功 → 再更新超限值才失败。
标记文本含列名与完整 CHECK 表达式，因此 CHECK 类按「出现 `CHECK constraint failed`
且含受限列名」识别，与触发器标记区分开。

#### 3.1.3 标记 → 类别（按裁定，不做合并）

| 标记 | 处理原则 | 类 |
|---|---|---|
| `stale_task_write`、`stale_projection_revision` | 按**租约/CAS 冲突**处理，不计真实故障；但**不得未经核对就返回成功** —— 必须回到权威状态判定（如 `verifyBuildActivated`） | B |
| `guard_requires_expected_revision` | 缺少**必填契约**，不是正常竞态，归确定性错误 | D |
| `cursor_regression` | **不允许一律暂缓**；正常流程中出现即需诊断的不变量违规 | D |
| `build_requires_building_flag` | **不能无条件归 B** —— 按构建启动 CAS 与权威状态判断：CAS 失败属竞态，状态本身不成立属实现/契约问题 | B 或 D（依权威状态） |
| JSON / 大小 CHECK | 确定性约束错误，**不走无限重试** | D |
| 无标记的其他存储异常 | 有限重试（阈值 5 + 退避档位） | C（默认兜底） |

#### 3.1.4 测试分两层（按裁定）

| 层 | 用例形态 | 断言 |
|---|---|---|
| **单层（单一失败条件）** | 只违反一个条件，且用独立的 scope | **断言精确标记**（如 `lease_epoch_mismatch` 必须是 `stale_task_write`，不能接受其他标记）；同时断言该条件成立前的前置操作成功（如「置 `building=1` 后插入 build 成功」） |
| **多层（多条件同时失败）** | 故意同时违反多个条件 | **允许返回已知标记之一**，但必须断言：① 整批回滚（无部分写入）；② **不返回错误成功回执**；③ 类别判定不依赖拿到的具体是哪一个标记 |

**两层都不得依赖触发器执行顺序**；测试只断言「类别 + 回滚 + 无假成功」，不断言具体触发器名。

「内部精确识别受控错误标记」与「禁止输出敏感错误文本」是两件事，二者同时满足：识别要准，输出要净。

### 3.2 分类表（修订）

| 类 | 判据 | 收尾 | `failure_count` | 退避 | 结果 |
|---|---|---|---|---|---|
| **A 正常等待** | 预算保留、等前序事件、正常续页、构建被上游中止后重排 | `deferTask(availableAt)` | 不增加 | 按等待原因 | `retry / deferred_*` |
| **B 已识别竞态** | 转换层识别为租约/CAS 竞争；或收尾 `rowsWritten === 0`；或 `verifyBuildActivated` 为真 | `noop` / `completed` | **不增加** | — | `lease_lost` / `build_activated` |
| **C 临时存储故障** | 转换层未识别、且不属于 D 白名单的存储异常（**默认兜底**） | `failTask(code)` | **+1** | 30/60/120/240/480 s | `retry` → 第 5 次 `needs_attention` |
| **D 确定性契约/大小错误** | code ∈ 白名单 | `parkNeedsAttention(稳定 code)` | **不增加**（裁定：直接停车、记录确定性原因；已有计数不抹除） | — | `needs_attention` |
| **E 收尾自身不可用** | `failTask`/`parkNeedsAttention` 自身抛错；**或预算已耗尽且连收尾预留都不足** | 保留租约（可用时），返回明确失败结果 `budget_exhausted_no_closeout` | 不增加（不得谎报已持久化） | — | 交恢复机制，**保留恢复路径** |

**C 是默认兜底**：凡转换层未识别、又不在 D 白名单内的，一律按 C 处理并**有限重试**（受阈值 5 与退避档位约束），不会无限暂缓。

**D 类白名单**（闭合集合）：
`changes_too_large`、`commit_batch_too_large`、**`build_state_too_large`**（§2.5，构建状态超限专用）、
`build_read_limit_exceeded`（§2.2）、`build_continuation_invalid`、`build_no_progress`、
`invalid_page_size`、`projection_head_missing`、`implementation_budget_violation`（§3.2.1）、
以及由转换层（§3.1.3）归一进来的：`cursor_regression`、`guard_requires_expected_revision`、
**CHECK 类**（`storage_check_violation`，含 `continuation_json` / `summary_json` 超限）。

**`build_requires_building_flag` 不在此白名单** —— 它是**条件性**的：按构建启动 CAS 与权威
状态判定，CAS 竞争归 B，状态本身不成立归 D（§3.1.3）。

**`budget_exhausted` 不在 D 类白名单内** —— 见 §3.2.1。

#### 3.2.1 预算耗尽的三类分流（**修正**）

原稿把 `budget_exhausted` 一律归 D 类「确定性、重试无意义」是**错的**：预算是**每次调用独立**的，
下一次调用完全可能正常处理。按情形分流：

| 情形 | 判定点 | 处理 | 类 | `failure_count` |
|---|---|---|---|---|
| **主动发现余量不足** | 阶段闸门预检（§5.3）发现 `剩余 < 下一阶段最坏成本 + 4`，尚未消耗 | `deferTask`，code `budget_reserve_insufficient`，**正常暂缓** | **A** | **不计真实失败** |
| **运行中耗尽，收尾预留仍足** | 业务阶段中途耗尽，但预留 4 次未动 | 按原路径收尾：竞态 → B；存储异常 → C（`failTask`） | B / C | 按各类规则 |
| **运行中耗尽，收尾预留也不足** | 连收尾都发不出去 | 明确失败 `budget_exhausted_no_closeout`，**保留租约与恢复路径，不谎报已保存状态** | **E** | 不计 |
| **代码路径必然超出固定配额** | 实测/断言发现某路径的**下限**就超过配额（非数据所致） | 独立诊断 `implementation_budget_violation`，停车并标记为实现问题 | **D** | 不计 |

要点：**不能把所有预算耗尽都归为永久错误**。只有最后一类才是实现缺陷；前三类都是运行时状态，
必须保留下一次调用恢复的可能。

**分类覆盖范围（修订）**：不只是最终 `io.db.batch`。以下阶段同样接入转换层与分类：
- `readStaged` 的 staging 读回；
- continuation / summary / 行值的序列化与字节测算；
- 归档对象 JSON 的构造与哈希；
- 收尾写（`failTask` / `park` / `completeTask`）自身。

### 3.3 零行收尾：调用方必须先查写入结果（**修订新增**）

实测：`failTask` 即使 `rowsWritten === 0`，其返回值仍可能给出 `state: "pending"`（判定式含 `rowsWritten && …`）。因此：

- 调用方**必须先检查 `rowsWritten`**，`rowsWritten === 0` 时按 **B 类**（租约被接管）处理，**不得声称已保存退避或失败计数**；
- 返回结构需明确区分「已持久化退避」与「未写入」两种结果，供调用方与测试断言。

### 3.4 成功清零：在成功事务内处理，不靠人工重放（**修订新增**）

实测：`completeTask` 只写 `state/lease`，**没有** `failure_count = 0`。`requeueNeedsAttention` 的清零属于**人工重放**路径，不能替代成功清零。

规则：

- 任务成功收尾（构建页完成、构建激活、增量投影完成）时，在**同一个成功事务内**把 `failure_count` 归零；
- **不得把「scope 内其他任务成功」当作本任务成功**：清零只针对本任务自身；
- 人工重放（`requeueNeedsAttention`）的清零语义保持不变。

### 3.5 与 Rev6 addendum §8 的对齐

| §8 契约 | 现有 | 本方案 |
|---|---|---|
| 真实故障计数 | `failTask` 已有，投影路径未接 | 接上（C 类） |
| 按规则退避 | `FAILURE_BACKOFF_SECONDS` 已有 | 同上 |
| 连续 5 次 → `needs_attention` | `FAILURE_COUNT_THRESHOLD = 5` 已有 | 同上 |
| 连续 5 次「告警」 | **无任何通知出口** | 按裁定：本轮做持久化 `needs_attention` + 稳定原因 + 脱敏结构化日志（见 §3.6）；外部通知留可观测性工作包，发布前闭环 |

### 3.6 告警口径（裁定落实）

- 状态转换**成功之后**才写日志；转换失败不写成功日志。
- 日志为脱敏结构化字段：`taskId`（可哈希截断）、`taskType`、`outcome`、`failureCount`、`threshold`、`stableCode`、`at`；**不含**原始 `message`、SQL、绑定参数、用户内容。
- 文档与日志文案中**不得**将该日志表述为「通知已送达 / alert sent」；外部通知不在本轮。

## 4. G2-F3 [P1] 重放完整性校验与测试矩阵（修订）

### 4.1 现状缺口（不变）

### 4.2 范围契约：扫描窗口 vs 实际消费范围（**修订重写**）

原稿要求「实际序号首尾相接」是错的。反例：A 用户两页分别消费 `[1,3]`、`[5,7]`，中间序号属于 B —— 两页实际范围不连续，但完全合法。

区分两个概念：

| 概念 | 定义 | 连续性要求 |
|---|---|---|
| **扫描窗口** | 本页**起始游标** → **消费后游标**，**半开区间 `[scanFirstCursor, scanCursorAfter)`** | 相邻页窗口**首尾衔接**：第 n 页 `scanFirstCursor` = 第 n−1 页 `scanCursorAfter`。窗口是游标区间，允许内含他用户序号 |
| **实际消费范围** | 本页真正消费的 `{ consumedFirstEventSeq, consumedLastEventSeq, consumedCount }` | **不要求**与他页数值连续；只要求它对应本页读取数组的**非空前缀** |

约束：

1. 消费结果必须是读取数组的**非空前缀**：`consumedCount` 为**安全整数**且 `1 ≤ consumedCount ≤ events.length`；
   `events.slice(0, consumedCount)` 的 `eventSeq` 严格递增。
   **第一条消费事件、最后一条消费事件、消费后游标三者全部由引擎从前缀派生**，不由 reducer 自报：
   `consumedFirstEventSeq = events[0].eventSeq`、
   `consumedLastEventSeq = events[consumedCount - 1].eventSeq`、
   `scanCursorAfter = consumedLastEventSeq + 1`；
2. 因此恒有 **`consumedLastEventSeq === scanCursorAfter − 1`**（相等，不是 ≤）；
3. **保留 `4f69982` 的双上界保护**：`scanCursorAfter ≤ lastFetchedSeq + 1` 且 `≤ targetEventSeq + 1`，不满足即 `build_no_progress`（D 类）；
4. **不得**仅凭 `nextEventSeq − 1` 就断言它一定是一条实际消费的事件（合法空页/零消费时不成立）；需要「实际消费的最后一条」时，取 `events[consumedCount − 1].eventSeq`，并同时校验 `consumedCount ≥ 1`；
5. **manifest 与页包各自明确使用哪一种范围**：
   - **页包** `firstEventSeq` / `lastEventSeq` = **实际消费范围**，并附 `consumedCount`；
   - **manifest** `firstEventSeq` = 整个构建的首个实际消费事件（或 `null`），`lastEventSeq` = 冻结目标 `targetEventSeq`；manifest **不要求**页间数值连续。

覆盖判据（替代原「首尾相接」）：

```
page[1].scanFirstCursor === manifest.firstEventSeq   （或 manifest.firstEventSeq 为 null 时为空构建）
page[n].scanCursorAfter === page[n+1].scanFirstCursor   对所有相邻页成立
page[last].scanCursorAfter === targetEventSeq + 1
每页 consumedCount 为安全整数且 1 ≤ consumedCount ≤ events.length
每页 consumedLastEventSeq === scanCursorAfter − 1（相等）
page[n].scanCursorAfter === page[n+1].scanFirstCursor（窗口衔接，依半开区间）
```

**页包必须实际保存两个扫描游标**（`scanFirstCursor`、`scanCursorAfter`），
否则离线重放无从验证窗口衔接 —— 仅保存实际消费范围不足以证明「中间没有整段被跳过」。

他用户造成的序号空洞由「扫描窗口内含未消费序号」天然容纳，**不要求** `consumedLastEventSeq(n) + 1 === consumedFirstEventSeq(n+1)`。

**两处明确例外**：

- **空构建的 `firstEventSeq = null` 是安全整数校验的明确例外**（§4.3 S4），校验器不得因它非整数而拒绝；
- **`events.length` 可为 0**（合法空页），此时不适用 `consumedCount ≥ 1`。

### 5.3 预留与总量

- **收尾预留 4 次**（覆盖最坏收尾路径 `failTask` 2 + `verifyBuildActivated` 2）。

- **「检查还剩 4 次」不等于「保留 4 次」**（原稿 `assertBudgetReserve(io, 4)` 只在入口查一次不成立：
  查完之后业务阶段仍可能把那 4 次花掉）。改为**每个业务阶段开始前的闸门**：

  ```text
  剩余预算 ≥ 下一阶段最坏成本 + 收尾预留 4
  ```

  不足则**不进入该阶段**，直接转入收尾（A 类 `budget_reserve_insufficient`）。
  各阶段最坏成本（依 §5.1）：领取与装载 4、首页 `MIN` 查询 1、页读取 1、
  `readStaged` 4（引擎强制）、提交 1。
